## 0. 一句话

**一个模型认两类物，六个格子决定「取哪儿」，两个料盒决定「放哪儿」。**
模型两条线共用同一份 `.pt`（只是传输方式不同）；网格两条线各有一份坐标，**互不换算**、靠 `cell_id` 对齐。

## 1. 目标检测模型

### 1.1 是什么

`exp3_public/weights/best.pt` —— **22,532,202 字节（21.5 MiB）**，YOLOv8s 检测权重。

权重文件内嵌的训练元数据（用 `zipfile` 读 `best/data.pkl` 可自重放，命令见 §5）：

| 字段 | 值 | 说明 |
|---|---|---|
| `names` | `['cup', 'mouse']` | **类别表的唯一权威**；索引即顺序 → `0=cup`、`1=mouse` |
| `task` | `model` | 检测任务（不是 `segment` / `classify`） |
| 起步权重 | `yolov8s.pt` | **s = small 档**，不是 n / m / l |
| 训练数据 | `public_data/balanced/data_balanced.yaml` | 均衡后的公开数据划分 |
| run 名 | `combined_model_v3` | 训练工程内的 run 目录名 |

**来源**：实验一《目标检测》的训练产物，实验三**不重训、不复现训练流程**，直接复用同一份权重
（三仓关系见 [`../README.md`](../README.md) 顶部表：实验一 `masai114514/object_detection_lab`）。
所以本文不描述训练超参 —— 训练归实验一，实验三只说「怎么用」和「用出来多少」。

> 上表每一项都是**从权重文件里直接读出来的**（`zipfile` 打开 —— `.pt` 本质是个 zip 包，再在
> `best/data.pkl` 的 pickle 流里做字符串前缀/精确匹配），**不需要 torch、不需要 ultralytics**。
> 这一点在答辩现场有用：任何一台机器都能当场重放上面那张表，不用先装环境。命令见 §5 文末。

### 1.2 入库策略：权重不进 git

`.gitignore` 明确忽略 `weights/*.pt` 与 `weights/*.onnx`（22 MB 二进制不宜进版本库），
随交付包分发（U 盘 / 微信）。

由此得到一条容易被答辩问到的边界：

- **clone 下来能跑离线单测**（`sort_core` / `examples` / `tests` / `config_check.py`）—— 完全不需要权重；
- **要跑识别（仿真或真机）才需要 `best.pt` 放到 `weights/`** —— 缺失时检测节点/检测函数会立刻报错，不会静默降级。

### 1.3 两个「置信度门限」不是一回事（本文最常被问错的一处）

| 参数 | 值 | 写在哪 | 语义 |
|---|---|---|---|
| 推理门限 `conf` | **0.25** | 检测节点参数 / 真机检测函数参数 | 低于它的框**根本不输出** —— 对下游等于「这东西不存在」 |
| 验收门限 `conf_min` | **0.5** | `config/task.json`（两套都有） | 框给了，但 `conf < 0.5` → 任务侧判 **`unrecognized_object`** 跳过 |
| 推理尺寸 `imgsz` | **640** | 检测节点参数 | 与训练时一致；**改它等于改「模型实际看到的物体有多大」，见 §4** |

⇒ **「没检出」和「检出但没作数」是两种不同的现象，日志里也长得不一样**：
前者这一轮桌面上就是没有它（可能因此判 `no_target` 正常结束），后者在 `records.jsonl` 里留一条
`decision=skip` / `skip_reason=unrecognized_object`。答辩时如果把这两件混成一件说，会被追问。

### 1.4 两条线传输方式不同，模型完全相同

| | 仿真线（ROS 2） | 真机线（**无 ROS**） |
|---|---|---|
| 入口 | `sensor_msgs/Image` → `cv_bridge` → YOLO → `vision_msgs/Detection2DArray` | 普通 Python 函数：`detect(frame) -> [{'cls','conf','bbox'}]` |
| bbox 口径 | **归一化 [0,1]、原点左上、中心 + 尺寸** | **像素 xyxy** |
| 骨架 / 实现 | `exp3/ros2/reference/detection_d2a_node.py` | `exp3/real/camera.py` 的检测器接口 |
| 权重 | `weights/best.pt` | **同一个** `weights/best.pt` |

两点必须说准：

1. **两条线喂给任务控制的东西是同一种**：ROS 侧在进 `sort_core` 之前就把归一化还原成了像素
   （按 `config/task.json` 的 640×480 还原），所以 `TaskController.scan()` 缝隙的两侧契约一致 ——
   **换平台不改接口**，这也正是整套设计的卖点。
2. 归一化 bbox 是**队伍口径，不是 `vision_msgs` 规范要求的**（`.msg` 根本表达不了这个约束）。
   答辩若被问到，照这个说，别说成「spec 规定的」—— 这句提醒原文写在
   `ros2/reference/detection_d2a_node.py` 的注释里。

⇒ 因此 **模型训练与调参只做一次**，两条线共用；仿真线改分辨率必须三人同步（像素尺度变了，标定作废）。

## 2. 类别说明

### 2.1 类别集合与索引

| 索引 | 类别名 | 语义 | 权威来源 |
|:---:|---|---|---|
| 0 | `cup` | 杯子 | `best.pt` 的 `names[0]` |
| 1 | `mouse` | 鼠标 | `best.pt` 的 `names[1]` |

只有这两个类别。**三处必须一致**：

```
best.pt 的 names  ⊂   task.json 的 classes   ↔   bins.json 的 class_to_bin 的键
    ['cup','mouse']       ["cup","mouse"]          {"cup":"bin_cup","mouse":"bin_mouse"}
```

⚠ **自检器只能查后两处** —— `config_check.py` 不读 `.pt`（它不想依赖 torch / ultralytics）。
`best.pt` 与其右侧的对齐靠**人当面核**：跑 §5 文末那条只用标准库的命令，把 `names` 打出来比一眼。
这是本工程里少数「结构自检覆盖不到、必须人工确认」的点之一，答辩若被问到对齐机制，要如实这么说。

- 数字索引（`0` / `1`）**只在 ROS 侧 `ObjectHypothesis.class_id` 里出现**；
  跨过缝隙之后一律按**类别名字符串**走 —— `sort_core` 不认识索引。
- 类改名或加类，等于同时改权重、`task.json`、`bins.json` 三处，且要重跑自检；
  只改一处会被自检器拦下（`task.classes` 里没有料盒映射的类别 = ERROR，注释原文：
  「该类别全被判 unrecognized」）。

### 2.2 两个类别之外的东西会怎样

诚实版答案分两种情形，**不要把两种说成一种**：

| 情形 | 现象 | 日志 |
|---|---|---|
| 模型压根不认（不在 `names` 里） | 根本不出框 → 该物体在系统眼里**不存在** | 无记录；严重时整轮被判「桌面已空」`no_target` |
| 出框了，但是未知类或 `conf < conf_min` | 出框 → 判不可执行 → 跳过 | `records.jsonl` 每条 `decision=skip` / `skip_reason=unrecognized_object`（同一格同一类只记一次） |

注意 `taxonomy.py` 把「未知类别」与「置信度 < conf_min」归成了**同一个 reason**
（`REASON_UNRECOGNIZED = 'unrecognized_object'`，源码注释：「未知类别 或 置信度 < conf_min」）——
所以要区分这两者只能看记录里的 `cls` 与 `conf` 字段本身。

### 2.3 类 → 料盒

| 类别 | 料盒 id | 料盒中心坐标 |
|---|---|---|
| `cup` | `bin_cup` | `config/bins.json`（仿真占位）/ `config_real/bins.json`（真机待回填） |
| `mouse` | `bin_mouse` | 同上 |

自检器对这张映射的检查规则（`config_check.check_bins`）：

- `class_to_bin` 的每个 value 必须在 `bins` 里，且 `bins[bid].cls` 要对得上（**双向一致**）；
- `task.classes` 里**每**一类都要有料盒映射（缺 = ERROR）；
- 一类对应多个料盒 = WARN（分类仍成立，但浪费格）。

**几何约束（硬件决定，不是设计选择）**：料盒必须和网格在**同一张台面**上 ——
EP 臂水平行程只有约 0.22 m、垂直约 0.15 m，摆不下第二个台面
（原文写在 `config_real/bins.json` 的 `_comment`，2026-09-15 硬件确认）。

### 2.4 场地布置的一个提醒

人是可以布置场地的（这是实验设置，不是作弊）；《实验3 实验要求》§六 禁的是**替系统做类别判断**和**替系统触发动作**。
若现场有既不属于 cup 也不属于 mouse 的物件需要「忽略」，把它**放到网格之外**即可 ——
框中心落在所有网格之外会被判 `out_of_grid` 跳过（见 [`异常测试记录.md`](异常测试记录.md) #3 实测记录），
不需要也不允许人工在系统里「告诉」它是什么。

## 3. 桌面网格配置

### 3.1 两套坐标，一张对照表

| | 仿真线 | 真机线 |
|---|---|---|
| 文件 | `exp3/config/grid_cells.json` | `exp3/config_real/grid_cells.json` |
| 坐标系 | 桌面平面机器人系（x 向前、y 横向，米） | 机器人系 `x_m` / `y_m`（米） |
| 怎么来的 | 「仿真 L1 布局」，由 Gazebo 场景**已知格心的实际图像投影**测得 | 「★真机现场用卷尺量的实际网格」—— 胶带在桌面贴出格子，每格两角是**量**出来的 |
| 当前状态 | ✅ 可用（`config_check.py --strict` 通过） | ⏳ **6 格全是「示例, 待回填」占位**，`calibration.status = uncalibrated` |
| 量的人 | 仿真线 | 现场持机人（做法见 `config_real/grid_cells.json` 的 `calibration.note`） |

**两份文件互不覆盖、必须分目录**：仿真线那份是场景里测得的布局坐标，真机线那份是 EP 现场实测值，
两套数**不可能一样**；`sort_core` 只吃「被指定的那一份」，不关心它在哪个目录 —— **换目录即换场景，代码一行不改**。

### 3.2 文件结构（两套完全相同）

```json
{
  "cells": [
    {"id": "c1", "row": 0, "col": 0, "x0": …, "y0": …, "x1": …, "y1": …},
    …     6 条：row ∈ {0,1} × col ∈ {0,1,2}
  ],
  "pick_z_m":   …,   // 取物高度
  "object_z_m": …    // 物块高度
}
```

- 每格由**两个角点** `(x0,y0)-(x1,y1)` 定义矩形，**格中心即取放目标点**（`geometry.cell_center`）；
- 实际情况：

| | 网格跨度 x | 网格跨度 y | 单格尺寸 | `pick_z_m` | `object_z_m` |
|---|---|---|---|---|---|
| 仿真 | 0.065 → 0.165 m | −0.120 → +0.120 m | 50 mm (x) × 80 mm (y) | 0.138 m | 0.018 m |
| 真机（示例值） | 0.060 → 0.190 m | −0.135 → +0.135 m | 60 mm (x) × 90 mm (y) | 0.138 m | 0.025 m |

### 3.3 ★ 两套坐标「不需要互相换算」—— 靠 `cell_id` 对齐

这是真机线最容易被讲乱的一处，`config_real/grid_cells.json` 的 `_comment` 里写得很死：

- `config_real/grid_cells.json` 的坐标**只在识别 / 定位这条线上用** —— 它的唯一职责是回答
  **「这个检测框落在哪一格」**；
- **EP 的底盘 / 臂位姿在 `config_real/ep_waypoints.json`** —— 它的职责是回答
  **「要取那一格，底盘和臂该怎么摆」**，**按 `cell_id` 与网格对应**（`c1` → `cell_pose.c1`）；
- 两者之间**不需要任何坐标变换**。同一格子在两个文件里各有一份表示，靠 `id` 对齐即可。

⇒ 一句话：**网格管「在哪」，位姿表管「怎么去」。** 第四份与本节相关的记录是 `bins.json`（料盒中心坐标）——
四份记录各自独立署名、独立 `calibration` 块，状态互不牵连（见 §5 清单）。

### 3.4 判格规则（代码位置与顺序语义）

`sort_core/geometry.py::locate(bbox_xyxy, calib, cells, image_size)` 是唯一入口，纯函数、离线可测：

1. 框中心 `px, py` = bbox 两角的平均（`bbox_center`）；
2. 中心**出画面**或**映射失败**（奇异/退化）→ 返回 `in_view=False`，调用方记 `out_of_grid`；
3. `px_to_table` 按 `camera.calib` 把像素换成桌面点（两种模式见 §3.5）；
4. `point_to_cell` 按 `cells` 的**文件顺序**返回**第一个**命中的格子；不在任何格 → `cell=None`，同样记 `out_of_grid`。

两条由实现决定、必须写进说明的推论：

- **格子重叠 = 判定歧义**。自检器把重叠报成 WARN（原文：「两物落重叠区会判定歧义」）——
  所以别让格子重叠，也别为了多塞一格而在重叠区里赌顺序；
- **顺序有语义**：真重叠时先出现的格子赢。这是「实现事实」，不是「应该这样做」。

### 3.5 相机→桌面的两种标定模式

| `camera.calib.mode` | 用在 | 数学 | 前提 |
|---|---|---|---|
| `rectilinear` | 仿真线（正俯视） | `px = offset_px + scale_px_per_m × (x_m, y_m)` | **光轴垂直向下** |
| `homography` | 真机线（斜俯视） | `H`(3×3) `@ [px,py,1]` → 桌面点（除以 w） | 任意俯视 / 透视 |

- **真机必须用 `homography`**：现场没有相机支架，做法是把相机垫高斜俯视
  （`config_real/task.json` 里明确写着「斜俯视 ⇒ 要换成 `mode: homography` + 3×3 H」）。
  用 4 个已知点解 H（最小二乘 / DLT），**判据：反投影误差 ≤ 半个格子宽**；
- `rectilinear` 下改分辨率必须重标（像素尺度变了，旧标定直接作废）；
- 两种模式都是纯函数，`tests/test_geometry.py` 离线覆盖 —— **标定没做完也能验证代码**。

### 3.6 未标定不许开跑（设计如此，不是故障）

```bash
python3 config_check.py --config-dir config_real --require-calibrated
```

当前输出：**结构检查全过**（grid / bins / camera / cross / ep 位姿表契约一致），
但 **14 项未标定 ERROR** —— 这正是设计要的结果：`real/run_real.py` 的第一件事就是过这道闸门，
**没量过的坐标不许驱动机械臂，连 `--dry-run` 都被拦**，且拒绝时连机器人都不会去连。
其中与本文直接相关的有 4 类：

1. `camera.calibration.status ≠ calibrated`（相机标定没做完）；
2. `calibration.by` / `date` / `venue` 为空（标定人 / 日期 / 场地要留档）；
3. `camera.calib` 仍是占位（要换成 `homography` + H，并删 `_note`）；
4. `grid_cells.json` 未标定，6 个格仍带 `_note: 示例, 待回填`。

## 4. 已知限制：等效像素宽是硬门槛

本节是本文最该单独看的一节 —— 它决定了**现场取景怎么架**，也决定了答辩时「识别效果」该怎么答。

### 4.1 域探针结论（2026-09-21，960 帧，原生渲染）

自变量是**网络实际看到的等效像素宽**（= `40 × 640 / S`，`S` 为取景窗口边长；`S = 640` 即整桌入镜），
判据 `IoU ≥ 0.30` 且类别正确，`conf_min = 0.25`：

| 等效像素宽 | cup 召回 | mouse 召回 |
|---|---|---|
| 40 px（**整桌入镜** S=640） | 10–90% | **0–20%** |
| 60 px（S=427） | 60–100% | 10–30% |
| 80 px（S=320） | 100% | 20–40% |
| 100 px（S=256） | 100% | 30–60% |
| 120 px（S=213） | 100% | 30–40% |

（每格是 tilt 0°/30°/45°/60° 四档的范围；`cup` 在 40 px 档的 90% 会一路掉到 60° 时的 10%，
明细与两类合并表见 `exp3_domain_probe/SUMMARY_zoom.md`。）

> ⚠ 该域探针目录**不在本仓库内**（它是实验三的离线分析产物，含 `probe.py` / `probe_zoom.py` /
> `probe_crop.py` 与 960 帧合成样本），所以上面这张表在本仓库里**没有可复跑的东西** ——
> 它是**实验数据**，不是代码。引用时请连 `SUMMARY.md`（74 KB 主表）、`SUMMARY_zoom.md`、
> `SUMMARY_crop.md` 三份一起交，答辩时以这三份为准。

三条必须一起说：

1. **mouse 是短板，而且不是「分低了」、是「压根不出框」** —— 40 px 档有 80–100% 的鼠标帧**一个框都没有**；
2. **这是原生渲染**（用更小的取景窗口 S 重新渲染，`S=320` 即取景收窄到一半），
   **不是把整帧放大** —— 所以数字可信；
3. ⚠ **结论只对「采集时看到的等效像素宽」成立，事后裁切 / 放大救不回来**。
   `exp3_domain_probe/SUMMARY_crop.md` 的对照很硬：mouse 在 60 / 80 / 110 px 档上，
   裁切 ROI 后的召回**普遍比整帧更差**（60 px 档 tilt 0°：整帧 90% → 裁切 30%）——
   信息在降采样那一步就丢了，裁切只能把丢掉的东西放大。cup 的情况相反（40 px 档裁切能从 20–50% 提到 100%），
   但**决定因素仍是采集那一刻的等效像素宽**。

⇒ 唯一有效手段：**采集时就把取景收窄**，让工作区 / 物体在画面里落在**等效 80–120 px** 区间。
这件事**没法在家拍板**（取决于现场支架多高、多远、工作区多大），所以现场必须有 §4.2。

### 4.2 现场 30 秒自检（开跑前必跑一次）

```bash
python3 real/vision_check.py                 # USB 相机连抓 10 帧
python3 real/vision_check.py --frames 20     # 多抓几帧看稳不稳
python3 real/vision_check.py --camera image:test.jpg   # 用存图（在家先试布置）
python3 real/vision_check.py --out frames/   # 存带框标注图，肉眼复核
```

**它回答一个问题：在这个取景下，`best.pt` 到底认不认得出桌上的东西。**

| 它报什么 | 它不做什么 |
|---|---|
| 每个检出：类别 / 置信度 / **像素宽高** / 框中心 /（标定好的话）落在哪一格 | 不连 EP |
| 按类汇总：检出数、**有效检出数**（`conf ≥ task.conf_min`，即真正算数的那些）、等效像素宽中位数 | 不过标定闸门 |
| 结论：按 **<60 危险 / 60–80 边缘 / ≥80 稳** 三区间逐类给判词 | 不改任何 config（**纯只读**，随时可跑） |
| 标注图存到 `--out`（默认 `vision_check_frames/`） | 相机没标定也能跑（格号栏显示 `-`，其余照报） |

⇒ 它是上表的**现场版本**：**表是离线算的，闸门是当场量的**。
它的存在意义正是「不要等跑完一轮、看日志才发现 mouse 全丢」。
